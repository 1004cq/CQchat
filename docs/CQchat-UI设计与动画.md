# CQchat UI 与 UI 动画设计

## 设计方向

CQchat 的界面不应该像普通社交软件一样鼓励用户持续浏览，也不应该像安全工具一样充满警告。核心感受应是：**附近的人可以被看见，消息状态可以被解释，身份可以被核验，数据不会偷偷经过服务器**。

视觉上延续 Logo 的深海军蓝、宝石蓝和电光青。背景保持安静，重要状态用颜色和短句表达，避免大面积渐变、霓虹光效和复杂网络图把产品做成“黑客风”。

## 核心导航

底部只保留三个入口：**附近、公频、私聊**。

“附近”是发现和连接中心；“公频”用于不加密的附近广播；“私聊”只显示已经建立过会话或收到过消息的对话。设置、帮助、权限说明和紧急清除放在右上角或个人菜单中，不占用一级导航。

## 页面一：附近

顶部显示 Logo、小标题“附近”，右侧是设置入口。标题下方放一个状态胶囊：`附近模式 已开启`，旁边显示蓝牙状态和当前电量影响提示。用户点击胶囊可以暂停附近模式，而不是进入复杂设置。

主体区域是设备卡片。每张卡片显示抽象头像、临时昵称、最近发现时间、连接路径和验证状态。验证状态分为“未验证”和“已验证”，使用文字加图标共同表达，不能只用颜色。卡片内不显示精确距离，优先显示“直连 BLE”“经 2 跳转发”“Wi‑Fi 局域网”等对消息可靠性更有帮助的信息。

当附近没有设备时，不显示空洞的插画，而是显示一个轻量的节点呼吸动画和一句解释：“打开附近模式后，CQchat 会寻找周围设备；不需要互联网。”下面提供“查看权限说明”。

## 页面二：私聊

私聊顶部显示对方昵称、验证徽章和当前传输状态，例如：`已验证 · 直连 BLE · 已加密`。连接状态应是可点击的，点击后展开一张底部卡片，解释当前消息是否经过中继、是否正在排队，以及为什么可能变慢。

消息气泡使用低对比度深色底，避免把安全色全部用在气泡上。自己的消息使用偏蓝色，对方消息使用深灰蓝。气泡底部统一放消息状态：排队、已交给附近设备、已送达、失败。不要只使用一个勾号来表示所有状态。

输入区保持熟悉：文字输入、语音、图片和发送。发送按钮只在有内容时激活。正在发送媒体时，气泡先显示本地缩略图和进度，不显示“已送达”；传输失败时保留重试和取消操作。

## 页面三：身份核验

核验页要让用户慢下来。顶部标题为“核验身份”，中间是 QR 区域，下方显示短指纹和“请与对方当面比对”。主要按钮为“确认已核对”，次要操作为“稍后再说”。

核验成功后，不跳转到复杂设置，而是返回对话页，并把对方卡片上的“未验证”转换成“已验证”。同时给出一次性提示：“以后看到这个身份时，CQchat 会提醒你。”

## 颜色与排版

- 背景：`#071126`，用于主背景。
- 一级卡片：`#101F3C`，用于设备卡片和底部面板。
- 主色：`#145BFF`，用于主按钮和选中状态。
- 强调色：`#08D9E5`，用于连接、扫描和活动状态。
- 已验证：`#66E3B4`，同时配合盾牌或勾选图标。
- 警告：`#FFC857`，用于权限、排队和电量提醒。
- 错误：`#FF6B7A`，只用于失败或危险操作。
- 正文：`#F7FAFF`；次要文字：`#9BAACC`。

标题使用系统无衬线字体，字重 650–700；正文使用 400–500。整体采用 8pt 间距系统，卡片圆角 18pt，按钮圆角 14pt，点击区域不小于 44pt。

## 动画总原则

动画只解释三类变化：**发现、连接、传输**。不做持续装饰性动画，不让节点一直闪烁，不让消息气泡弹跳。所有动画在低电量模式、辅助功能“减少动态效果”开启时都应降级为淡入、颜色变化或静态图标。

## 动效规范

### 1. 附近模式开关

开启时，状态胶囊从灰色过渡到蓝色，Logo 中心出现一次 3 节点连线动画。总时长 420ms，使用 ease-out。之后只保留每 3 秒一次、很轻的 2%–4% 光晕变化，不持续旋转。

关闭时不播放反向大动画，只让胶囊颜色在 180ms 内退回中性灰，并把节点动画立即冻结，避免用户以为后台仍在工作。

### 2. 发现设备

新设备出现时，从列表下方淡入并上移 8pt，时长 240ms。头像外圈做一次从 0.92 到 1.0 的缩放，时长 280ms。没有弹窗和提示音，避免附近人出现时打扰用户。

设备消失时不要立即删除，先降为半透明并显示“刚刚离开”，延迟 2–3 秒后再移除。这样可以避免 BLE 扫描抖动造成列表闪烁。

### 3. 建立连接

连接中使用围绕头像的单段弧线，从 0% 绘制到 100%，时长 700ms；弧线只循环两次，随后进入成功或失败状态。连接成功后，弧线变成一个小勾并淡出，验证徽章不自动出现，避免把“连上设备”误解成“确认了身份”。

### 4. 发送消息

用户点击发送后，消息气泡立即进入本地时间线，但底部状态显示“排队中”。气泡不弹跳，只进行 120ms 的淡入。状态依次变化时使用图标和文字的 crossfade，时长 160ms。

从“排队中”到“已送达”不使用飞行动画，因为消息可能经过多跳，飞行动画会给用户错误的路径暗示。可以在状态文字旁显示一条很短的进度线，在真实收到 ACK 后完成。

### 5. 多跳转发

在连接状态详情中，使用最多 3 个节点的静态小图展示当前路径。数据包沿路径移动一次即可，时长 520ms；不做无限循环。路径变化时使用 200ms 的淡入淡出，避免网络图频繁跳动。

### 6. 身份核验

QR 页面打开时，二维码从 96% 缩放到 100%，时长 220ms。扫描成功后，二维码区域被一个深色面板覆盖，显示双方短指纹逐段高亮比对，时长 500ms。用户点击“确认已核对”后，按钮显示一次勾选，时长 260ms，然后返回对话页。

核验失败时不使用摇晃整个页面。只让指纹区域出现一次 4pt 的左右位移，并在下方显示原因和“重新扫描”。

### 7. 权限说明

权限页从底部上移 280ms。每种权限用一个静态图标和一句解释。系统权限弹窗出现前，先完成应用内解释；用户拒绝后，不使用红色全屏提示，而是在附近页显示可恢复的“需要附近设备权限”卡片。

## 无障碍与性能

所有状态不能只依赖颜色。连接中、已验证、排队、失败都要有文本和图标。动态文字需要支持系统字体放大，卡片不能依赖固定高度。减少动态效果开启后，节点、路径和光晕动画替换为静态图标和 160ms 内的颜色过渡。

动效必须由状态驱动，而不是由定时器驱动。扫描没有结果时不运行高频动画；应用进入后台后暂停所有非必要动效；媒体进度使用真实字节进度。这样可以减少电量消耗，也能避免界面状态与实际网络状态不一致。

## 实现建议

SwiftUI 中可把 `NearbyModeState`、`PeerConnectionState`、`MessageDeliveryState` 和 `VerificationState` 建模为枚举，再由视图根据状态选择动画。Android Compose 使用同名状态模型和统一的 motion token，避免两端出现不同的时长和状态含义。

建议将颜色、圆角、间距、动效时长和缓动曲线集中在共享设计令牌中。协议状态名称也应直接复用到 UI，避免核心层叫 `acked`、iOS 叫“已发送”、Android 叫“已送达”而造成语义错乱。

## 优先实现顺序

先实现附近页、私聊页和核验页的静态状态；再实现附近模式开关、设备出现/消失、消息状态变化和核验成功动画；最后加入多跳路径和媒体进度。第一版不建议制作全屏网络动画、持续粒子背景或复杂 3D 转场。
