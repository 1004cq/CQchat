# CQchat 加密敏感代码安全审查报告

日期：2026-10-26  
范围：Android、iOS、Noise XX、身份绑定、会话管理、ACK、消息去重及包解析。

## 一、结论摘要

当前没有发现一个可以明确归类为“通过秘密值逐字节早退比较而泄露密钥”的直接 Timing Attack 漏洞。Ed25519 签名验证和 ChaCha20-Poly1305 AEAD 验证均由平台或密码库执行，代码中的 fingerprint、公钥、临时设备 ID 和消息 ID 比较属于公开标识比较，不是秘密密钥比较。

但是，本次审查发现了若干比传统 timing attack 更严重的协议完整性、可用性和身份认证问题：

| 优先级 | 问题 | 平台 | 影响 |
|---|---|---|---|
| P0 | iOS AEAD 解密失败仍递增接收 nonce | iOS | 远程伪造密文可令会话永久失步，后续合法消息全部无法解密 |
| P0 | ACK 未经过 Noise 认证 | Android / iOS | 攻击者可伪造“已送达”状态并重放 ACK |
| P0 | 私密包外层头未纳入 AEAD associated data | Android / iOS | 可篡改 sender、msgId、flags、ACK 标志等元数据 |
| P1 | 会话在身份 Hello 验证前即被视为可用 | Android | 存在临时身份混淆和 MITM 窗口 |
| P1 | 私密包对所有会话盲试解密 | Android / iOS | 放大 CPU 消耗，也使 nonce/来源绑定更难保证 |
| P1 | iOS 去重缓存无容量上限 | iOS | 可远程制造内存和 CPU 压力 |
| P1 | 未认证 step-1 可覆盖同一临时 ID 的握手 | iOS | 握手劫持/拒绝服务 |
| P1 | 握手密码学异常可能穿出回调 | Android | BLE/TCP 畸形输入可能导致服务级不稳定 |

## 二、真正的 Timing Attack 结论

### 2.1 未发现的风险

以下比较目前不涉及秘密值：

- Android `ByteArray.contentEquals()`：用于 X25519 公钥、Ed25519 fingerprint、消息 ID、临时设备 ID。
- iOS `Data ==`：用于相同的公钥、fingerprint、消息 ID、临时设备 ID。
- `IdentityCrypto.isVerified()` / `IdentityKeys.isVerified()`：用于公开 fingerprint 的集合查询。
- CryptoKit Ed25519 `isValidSignature`：由系统密码库负责签名验证。
- Android Bouncy Castle `verifySignature`：由密码库负责签名验证。
- ChaCha20-Poly1305 的 AEAD 校验：由密码库执行，不应自行替换为逐字节比较。

这些比较仍然可以在工程规范中统一封装，但目前没有证据表明它们会通过网络暴露私钥或认证密钥的逐字节信息。

### 2.2 必须保持的安全规则

如果未来出现以下比较，必须使用固定长度的 constant-time compare：

- HMAC/MAC tag；
- AEAD tag；
- 密钥派生结果；
- challenge-response secret；
- session token 或 bearer secret。

不要使用 `==`、`equals()`、`contentEquals()` 或手写循环比较这些秘密值。公钥和 fingerprint 可以普通比较，但必须保持固定长度和严格格式校验。

## 三、P0：iOS 解密失败递增 nonce

位置：

- `ios/CQchat/Protocol/NoiseXX.swift:283-298`
- 放大点：`ios/CQchat/Chat/ChatEngine.swift:351-360`

iOS `CipherState.decrypt` 当前在 AEAD 验证之前递增接收计数器。攻击者可以发送任意长度合规但认证失败的密文，使接收端 nonce 前进；随后真实发送方仍使用旧 nonce，所有合法消息都会解密失败。

更严重的是，iOS `ChatEngine` 会对所有已建立会话尝试解密未知私密包，单个伪造包可能消耗多个会话的接收 nonce。

### 修复建议

1. 解密时先读取当前 nonce，不要立即提交状态；
2. AEAD 验证成功后再递增 nonce；
3. 解密失败保持 nonce 不变；
4. 将解密状态封装为串行状态机，避免并发下重复提交；
5. 不要对所有会话盲试解密，应先根据已绑定的 sender/temp ID 路由到唯一会话；
6. 对连续认证失败进行来源、连接和临时 ID 级限速；
7. 连续失败达到阈值时安全废弃会话并重新握手。

Android 当前解密失败不递增 nonce，这一点是正确的，应让 iOS 与 Android 行为一致。

## 四、P0：ACK 未认证

位置：

- Android：`android/app/src/main/java/com/cqchat/app/chat/ChatEngine.kt:223-236`
- iOS：`ios/CQchat/Chat/ChatEngine.swift:267-270`
- ACK 生成位置：Android `314-319`，iOS `376-380`

ACK 当前携带明文消息 ID，并且被排除在去重处理之外。接收端仅凭 ACK 中的 16 字节消息 ID 就删除等待项并标记消息为 delivered。

攻击者不需要 Noise 密钥即可伪造 ACK。消息 ID 位于外层包头，可能被观察、转发或猜测。ACK 也可以被重复发送。

### 修复建议

优先将 ACK 作为对应 Noise 会话中的加密明文：

```text
PRIVATE(Noise encrypt(
    ACK || original_msg_id || direction || session_generation
))
```

接收端必须同时校验：

- ACK 来源会话；
- 目标 fingerprint；
- 被确认的消息确实处于 awaiting 状态；
- ACK 方向正确；
- 消息 ID 没有被确认过；
- ACK 不超过会话代次和有效时间。

如果暂时不能改成 Noise 私密 ACK，至少需要基于会话密钥的 MAC，并将 `(session_id, msg_id, direction, protocol_version)` 纳入认证消息。

## 五、P0：私密包外层头未纳入 AEAD

位置：

- Android `NoiseXX.kt:227-245, 414-445`
- Android `ChatEngine.kt:116-123, 163-187, 302-319`
- iOS 对应 Noise transport 和 `ChatEngine` 私密包路径。

当前 Noise transport 的 associated data 始终为空：

```text
AD = empty
```

因此以下外层字段没有被端到端认证：

- `sender`；
- `msgId`；
- `flags`；
- `ttl`；
- `version/type`，视当前调用路径而定。

攻击者不能凭此伪造私密明文，但可以篡改消息元数据：

- 修改 `msgId`，影响去重、ACK 和重试；
- 修改 `NEEDS_ACK`，强制或抑制 ACK；
- 修改 sender，造成来源混淆；
- 修改 TTL，改变中继行为。

### 修复建议

将不可变的端到端字段编码为稳定格式并传入 AEAD：

```text
AD = domain || version || type || flags || sender || msg_id
```

TTL 需要明确分类：

- 如果 TTL 允许中继节点修改，则不能作为端到端 AD；
- 如果 TTL 是端到端语义，则必须纳入 AD，任何修改都应导致认证失败；
- 不要让同一字段同时承担 hop-by-hop 和 end-to-end 两种语义。

## 六、P1：会话在身份认证前即被暴露

位置：

- Android `ChatEngine.kt:265-273`
- 特别是 `sessions.complete(temp)` 调用点。

Android initiator 收到 Noise step 2 后，立即发送自己的 Hello 并将会话标记为 complete。此时对端 Ed25519 公钥和绑定签名尚未收到和验证。

如果业务层在收到对方 Hello 前允许发送私聊消息，消息可能被发送给尚未认证的 Noise 静态身份。这是身份混淆/MITM 窗口，不是传统 timing attack。

### 修复建议

增加显式状态：

```text
HANDSHAKING
  -> NOISE_ESTABLISHED
  -> IDENTITY_AUTHENTICATED
  -> USABLE
```

只有进入 `IDENTITY_AUTHENTICATED` 后才允许：

- 暴露会话给私聊发送逻辑；
- 显示已建立或已验证；
- 将会话绑定到 Ed25519 fingerprint。

## 七、P1：对所有会话盲试解密

位置：

- Android `ChatEngine.kt:302-356`
- iOS `ChatEngine.swift:349-360`

收到私密包时，当前逻辑可能遍历所有会话并依次尝试解密。该设计有三个问题：

1. 任意攻击者可制造 O(会话数) 的 AEAD 计算；
2. sender 没有和会话的 remoteTempId 严格绑定；
3. iOS 当前 nonce 失败递增会将这个问题升级为会话破坏。

### 修复建议

使用：

```text
sender/temp_id -> 唯一 Noise 会话
```

只对映射到的会话尝试解密。解密成功后还要确认：

```text
packet.sender == session.remoteTempId
```

并且把 sender 纳入 AEAD AD。

## 八、P1：iOS 去重缓存无容量上限

位置：

- `ios/CQchat/Chat/DedupCache.swift:3-26`
- 调用点：`ChatEngine.swift:256-259`、`BleMeshService.swift:103-114`

iOS 去重缓存只按照 TTL 清理，没有最大条目数、LRU 或按来源配额。攻击者可以持续发送随机消息 ID，使缓存持续增长。

此外，去重登记发生在完整认证和业务解析之前，导致未认证包也能推动缓存增长。

### 修复建议

- 增加全局最大容量；
- 增加每个连接/来源的配额；
- 使用 O(1) LRU 或环形淘汰；
- 对广播、私聊、握手分别设置预算；
- 对未知类型、超长包、非法 TTL 先丢弃；
- 私聊消息优先在成功 Noise 解密后再登记去重。

## 九、P1：同一临时 ID 的握手可被覆盖

位置：

- `ios/CQchat/Chat/SessionManager.swift:32-36`
- 入口：`ChatEngine.swift:291-301`

`beginHandshake` 会无条件用同一个 temp ID 覆盖旧的临时握手。攻击者观察到真实 temp ID 后，可以发送伪造 step 1 覆盖正在进行的握手，使后续合法 step 2/3 失败。

### 修复建议

- 同一 temp ID 已存在活动握手时拒绝覆盖；
- 引入连接上下文或随机 challenge；
- 限制并发握手数量；
- 对 step 1 失败进行限速和退避；
- 只有完整且身份验证通过的握手才能替换旧会话。

## 十、P1：握手异常穿出 Android BLE 回调

位置：

- Android `ChatEngine.kt:253-299`
- `BleMeshService.kt:217-230, 387-393, 411-424`

畸形长度、AEAD 失败、低阶 X25519 公钥和非法状态都可能抛异常。当前握手入口没有统一捕获预期的协议/密码学异常。

### 修复建议

在握手入口统一处理：

```text
try:
    processHandshake(packet)
catch expected protocol/crypto error:
    sessions.abort(tempId)
    rateLimit(source)
    drop silently
```

异常不能穿出 BLE callback 或主处理线程。日志只记录受限的安全事件，不要输出密钥、完整密文或可被远程利用的详细状态。

## 十一、其他发现

### iOS 握手错误后仍继续写 step 3

位置：`ios/CQchat/Chat/ChatEngine.swift:303-314`

`initiatorRead2` 的错误被忽略，代码仍可能调用 `initiatorWrite3`。应使用 `guard let`，失败立即 `abortHandshake`，禁止继续推进状态机。

### iOS nonce 耗尽未处理

位置：`ios/CQchat/Protocol/NoiseXX.swift:267-286`

在 `UInt64.max` 前应安全关闭当前会话并重新握手，不应依赖整数溢出行为。建议增加消息数/字节数 rekey 上限。

### iOS 随机消息 ID 忽略随机源错误

位置：`ios/CQchat/Protocol/PacketCodec.swift:191-195`

`SecRandomCopyBytes` 失败时不应继续使用全零或未初始化的 buffer。应返回错误并停止发送。

### iOS Keychain 错误被当成“没有身份”

位置：`ios/CQchat/Crypto/IdentityKeys.swift:12-25, 103-114`

只有 `errSecItemNotFound` 才能触发首次生成身份。锁定、权限错误、数据损坏和服务不可用都应直接报错，不能静默生成新身份覆盖旧身份。

### Android 身份密钥以可变 ByteArray 暴露

位置：`android/app/src/main/java/com/cqchat/app/crypto/IdentityStore.kt:31-48`

`seed`、`x25519Private` 和 `ed25519Private` 是公开可变数组，且生命周期内没有清零。建议改为私有字段、仅返回副本，优先使用 Android Keystore 或硬件保护密钥。

### Android QR 解析异常

位置：`android/app/src/main/java/com/cqchat/app/crypto/IdentityStore.kt:57-62`

畸形 hex 输入可能抛 `NumberFormatException`。当前主要是本地 DoS，但未来若 QR 输入来自自动远程流程，应改为严格校验并返回 null。

### iOS 包解析允许尾随字节

位置：`ios/CQchat/Protocol/PacketCodec.swift:28-42`

当前只检查数据长度至少满足字段要求，可能接受尾随字节。建议改为精确长度校验，并明确拒绝未知 flags/type，避免跨端解析差异。

## 十二、建议修复顺序

### 第一阶段：立即修复

1. 修复 iOS 解密失败递增 nonce；
2. 停止对所有会话盲试解密；
3. 认证私密包外层 AD；
4. 将 ACK 改为 Noise 加密认证消息；
5. 握手异常统一捕获并 abort；
6. Android/iOS 都增加 sender 到会话的严格绑定。

### 第二阶段：身份和资源安全

1. 增加 `IDENTITY_AUTHENTICATED` 状态；
2. 禁止未认证会话进入发送和 UI 已连接状态；
3. 防止同一 temp ID 覆盖活动握手；
4. 为去重缓存增加容量和来源配额；
5. 修复 iOS step2 错误后仍继续 step3；
6. 为 nonce 耗尽增加安全关闭/rekey 机制。

### 第三阶段：密钥生命周期和平台健壮性

1. Android 长期密钥迁移到 Keystore；
2. iOS 区分 Keychain NotFound 与其他错误；
3. iOS 检查随机源错误；
4. Android QR 解析改为无异常安全解析；
5. 两端统一精确包长度和 flags/type 白名单；
6. 为未来 MAC/secret 比较引入统一 constant-time compare 工具。

## 十三、最终判断

从狭义 Timing Attack 角度：当前未发现明确的秘密值逐字节早退比较漏洞，密码库承担的签名和 AEAD 验证路径没有被手写逻辑破坏。

从整体密码协议安全角度：项目当前仍存在多个应优先修复的高风险问题，尤其是 iOS nonce 处理、未认证 ACK、未认证外层包头和身份认证前暴露会话。这些问题的实际风险高于普通网络定时侧信道，应在发布前处理。
