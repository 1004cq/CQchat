# CQchat 优化方案

## 结论先行

CQchat 的定位有差异化：它不是“没有网络时也能用的普通聊天软件”，而是“附近设备之间，不依赖账号、服务器和互联网的加密消息工具”。这个方向值得继续做，但当前仓库仍停留在产品和协议草案阶段，最需要优化的不是 UI，而是先把协议边界、后台能力和安全承诺说清楚。

当前方案最大的风险是把 iOS 和 Android 的后台能力想象成一致。Apple 官方文档明确说明，iOS 后台 Core Bluetooth 会合并扫描结果、降低扫描频率，应用被唤醒后也不能无限运行；系统仍可能因为内存压力终止应用。Android 官方则建议后台扫描使用 `PendingIntent`，长期连接通常需要 `CompanionDeviceService` 或 `connectedDevice` 类型的前台服务。[1] [2] 因此，CQchat 不应承诺“杀进程后仍然持续转发”或“后台永远在线”，而应把产品定义为“用户开启附近模式后，尽可能维持连接；系统允许时后台恢复”。

## 一、先收窄第一版承诺

第一版建议只承诺以下体验：用户打开附近模式后，可以发现附近设备；可以发送公频文字和一对一私聊；私聊可以通过二维码核对身份；消息在短暂离开 App 或连接中断后进入待发送队列；重新发现路径后自动重试；Wi-Fi 局域网可用于较大的加密媒体传输。

以下内容应明确标记为后续能力，而不是第一版的稳定承诺：长期后台 Mesh 中继、跨多跳的大文件传输、杀进程后的消息接收、无感知地持续广播、复杂群组加密和多设备同步。这样可以避免用户以为 CQchat 是一个在所有系统状态下都可靠工作的无线基础设施。

README 还需要把“公频广播不好追踪”和“身份可当面核对”区分开。未验证的附近设备可以使用短期轮换标识；一旦用户主动扫码确认，应用需要明确告诉用户这会建立一个可识别的长期身份关系。隐私不是“完全不可见”，而是让用户知道哪些信息会被附近无线设备观察到。

## 二、协议应先形成可执行的 v0.1 规范

现在的字段列表还不够实现。建议先建立一个独立的 `docs/protocol-v0.1.md`，同时提供一份机器可读的字段定义和跨平台测试向量。协议必须规定字节序、整数长度、字符串编码、最大包长、未知字段处理、版本协商、错误码、重试规则和超时规则。

建议将传输信封与加密载荷分层：

- 传输信封只负责转发和去重，包含协议版本、包类型、随机消息 ID、TTL、分片信息、优先级和加密载荷长度。
- 加密载荷负责会话消息、媒体密钥、确认信息和应用数据。
- 路由节点只需要看到转发所必需的信息，不应看到昵称、长期公钥、聊天正文或媒体类型以外的敏感信息。

`msg_id` 不应由时间戳或发送者指纹简单拼接得到。建议使用至少 128 位随机值，并规定去重缓存的生命周期、最大容量和淘汰策略。消息需要有明确的状态机：`created`、`queued`、`sent`、`relayed`、`delivered`、`failed`。用户界面只能在收到明确确认后显示“已送达”，不能因为数据写入本地队列就显示“已发送”。

TTL、过期时间和重试次数要分开。TTL 限制空间上的最大跳数；过期时间限制时间上的有效期；重试次数限制同一路径反复发送。每次转发都应减少 TTL，并在接近拥塞时降低低优先级媒体包的转发概率。不要只用“TTL 起始 7”作为全部拥塞控制策略。

分片协议需要支持乱序、重复、丢失和取消。每个分片至少需要关联 `message_id`、`fragment_index`、`fragment_count` 和完整性校验；接收端应有内存与磁盘上限，超过上限自动丢弃未完成对象。媒体传输要支持断点续传，否则 BLE 连接一断，大文件会从头开始，用户体验会很差。

## 三、身份与加密设计需要拆成三种概念

当前 README 把 X25519、Ed25519、Noise、二维码指纹放在一起，但还没有说明每把钥匙负责什么。建议明确拆分：

1. **长期身份密钥**：用于二维码核对和稳定身份表达。可以使用 Ed25519 签名密钥。
2. **会话密钥协商密钥**：用于 X25519 DH。不要把签名密钥和 DH 密钥混用，除非采用经过审计的标准转换方案并写入规范。
3. **会话与消息密钥**：由 Noise 握手和后续密钥派生产生，用于实际加密。

首次建立私聊时使用 Noise XX 是合理的，因为双方都可以在握手过程中传递静态公钥，并完成双向认证。Noise 规范把 XX 描述为通用的双向认证模式；握手完成后，应用可以使用握手哈希作为信道绑定，并自行决定何时 rekey。[3] 已经扫码核验过的联系人，后续可以考虑使用基于已知静态公钥的更快握手模式，但第一版不建议同时实现太多模式，避免跨平台不一致。

必须补充以下安全规则：

- 所有 AEAD nonce 的生成方式和重启后的恢复方式必须固定，不能依赖系统时间。
- 会话计数器和消息 ID 必须能防止重放；接收端要拒绝已经成功解密过的计数器或消息 ID。
- 会话状态损坏时要安全失败并重新握手，不能为了“尽量发出去”而复用未知状态。
- 公频消息虽然不加密，但应该使用签名广播，并让 UI 明确显示“公开消息”。
- 未验证身份、已验证身份和临时匿名设备必须有不同的 UI 状态，不能只显示一个昵称。
- 媒体文件的缩略图、文件名、大小和正文都属于可能泄露信息的元数据，应决定哪些字段加密、哪些字段可被中继看到。

第一版不上 Double Ratchet 可以接受，但 README 应明确这意味着什么：Noise 会话提供的是会话级的前向安全能力；离线排队、长时间未连接的消息和多设备场景需要单独定义密钥生命周期，不能笼统地宣传为“所有消息都有同等强度的前向保密”。

## 四、跨平台实现建议采用“共享核心 + 原生适配层”

项目要求 iOS 与 Android 共用一套协议，这一点应进一步落实为共用一套可测试的核心实现。建议使用 Rust 编写协议、编码、加密、分片、去重、重试和状态机核心，通过 UniFFI 或稳定的 C ABI 暴露给 Swift 和 Kotlin；iOS 使用 SwiftUI 与 CoreBluetooth，Android 使用 Kotlin 与 BLE API。这样可以减少两端各自实现二进制解析和加密状态机所产生的分歧。

原生层只处理系统能力：蓝牙扫描、广播、GATT 连接、前后台生命周期、权限、通知、Wi-Fi 局域网发现和 TCP/Socket。核心层不应直接依赖 CoreBluetooth 或 Android Bluetooth 类，否则共享协议会被平台细节污染。

目录建议从当前 README-only 状态逐步变为：

```text
core/
  protocol/
  crypto/
  routing/
  storage/
  test-vectors/

ios/
  CQChatApp/
  BluetoothAdapter/
  LocalStorage/

android/
  app/
  bluetooth/
  local-storage/

docs/
  protocol-v0.1.md
  threat-model.md
  test-matrix.md
```

不要一开始就同时实现所有功能。先让 iOS 与 Android 互发固定长度的加密文字，再逐步加入分片、转发、Wi-Fi 和媒体。每增加一种消息类型，都要同步更新规范、测试向量和两端实现。

## 五、传输层应做成“统一信封，多种载体”

蓝牙和 Wi-Fi 不应各自定义一套消息语义。两种传输都只搬运同一种加密信封。

BLE 适合发现、握手、小消息和短语音。建议使用明确的服务 UUID 与特征划分，控制发现包的体积，避免把身份、昵称和媒体信息塞进广播包。BLE 连接要有连接超时、单连接串行写入队列和背压机制，不能在多个异步回调中无序写入。

Wi-Fi 热点或同一局域网适合媒体和批量同步。mDNS 只用于发现本地服务，不要把身份放进服务名或 TXT 记录。TCP 连接建立后仍然传输已经加密的统一信封；不要因为“局域网看起来可信”就把正文改成明文。大包优先 Wi-Fi，失败后可退回 BLE，但应有明确的最大重试和取消逻辑，避免两个传输同时重复发送。

iOS 后台扫描和广播会被系统合并或降频，且后台唤醒后的处理时间有限。[1] Android 12 及以上还需要运行时申请 `BLUETOOTH_SCAN`、`BLUETOOTH_ADVERTISE` 和 `BLUETOOTH_CONNECT`；如果不从扫描结果推导物理位置，可以声明 `neverForLocation`，但官方也提示这可能过滤部分 BLE 信标。[4] 因此，权限和后台状态必须成为产品流程的一部分，而不是在开发末期补上。

## 六、产品体验应围绕“可验证”和“可解释”

首次进入应用时，不要直接弹出一串系统权限。应先用一页说明解释：为什么需要附近设备权限、附近的人能看到什么、关闭附近模式后会发生什么、系统可能在后台暂停哪些能力。用户开启“附近模式”后，再按实际需要请求权限。

主界面建议保持三个核心入口：附近、公频和私聊。附近列表显示临时设备、信号/连接状态和验证状态；私聊页面显示当前传输路径，例如“直连 BLE”“经 2 跳转发”“Wi-Fi 局域网”。这些信息不是装饰，而是帮助用户判断消息为什么慢、为什么排队。

二维码核验页面应同时展示昵称、短指纹和完整公钥指纹的可读片段，并明确“扫码后将把这个设备绑定为已验证身份”。对于未验证设备，默认限制自动接收大文件和自动转发，降低恶意设备消耗电量与存储的风险。

消息状态至少区分“本地排队”“已交给附近设备”“已到达对方设备”“对方已读”。如果无法确认，就显示等待或未知，不要用绿色勾号制造虚假的可靠感。

## 七、媒体功能要延后到基础消息稳定之后

图片和语音是 CQchat 的重要差异点，但也是最容易拖垮第一版的部分。建议按顺序实现：纯文字单跳、纯文字多跳、文本确认与重试、短语音、缩略图、图片分片、Wi-Fi 大文件和断点续传。

图片处理应在加密前完成压缩，缩略图也应独立生成并单独加密。媒体对象要有总大小上限、单片大小上限、磁盘配额和自动清理策略。语音使用 Opus 时，要把采样率、声道、帧长、最大时长和编码参数写进协议，而不是只写“使用 Opus”。

对低电量、拥塞和存储不足要有明确策略：优先发文字和确认，暂停大媒体；中继设备不应在没有用户同意的情况下无限缓存陌生人的大文件；接收端空间不足时要返回可解释的失败原因。

## 八、必须建立威胁模型和验收指标

建议新增 `docs/threat-model.md`，明确 CQchat 防御的对象和不防御的对象。至少要讨论：被动监听者、主动伪造设备、恶意中继、重放攻击、流量分析、设备丢失、应用被杀、恶意大包、密集设备造成的电量消耗，以及用户主动扫码后身份暴露的后果。

当前 README 已经写出“杀进程后仍可能被扫到有设备，不承诺隐身”，这是正确方向，但还需要把“隐私保护”拆成内容机密性、身份不可链接性、元数据保护、可用性和抗审查能力。一个方案通常不能同时把这些指标都做到最好，用户需要看到明确取舍。

第一版的验收不要只看“能不能发出去”，还应记录：发现设备的中位时间、单跳和多跳送达率、重复包比例、重连成功率、消息从排队到送达的 P95 延迟、BLE 与 Wi-Fi 的电量消耗、后台恢复成功率、媒体断点续传成功率、协议解析 fuzz 测试结果和两端测试向量一致率。

测试至少覆盖真实 iPhone 与 Android 设备，而不能只依赖模拟器。需要测试锁屏、切换 App、系统低电量、蓝牙开关、权限拒绝、应用被杀、设备重启、Wi-Fi 热点切换、多个中继同时转发、丢包和乱序。

## 九、推荐落地顺序

**阶段 0：冻结协议边界。** 产出协议 v0.1、威胁模型、消息状态机、错误码、测试向量和最小兼容矩阵。这个阶段不做 UI 大量开发。

**阶段 1：完成最小跨平台闭环。** 两端本地生成密钥，扫码展示指纹，BLE 单跳发现和私聊文字可用。消息必须可重放检测，应用重启后能安全重新握手。

**阶段 2：加入可靠性。** 增加 ACK、重试、队列、去重、乱序分片和明确的消息状态。先把单跳做到可解释、可测试，再开始多跳。

**阶段 3：加入 Mesh 转发。** 实现有限 TTL、转发去重、拥塞控制、优先级和中继缓存上限。用真实设备做三台、五台和十台的 RF 测试。

**阶段 4：加入 Wi-Fi 与媒体。** 统一加密信封，Wi-Fi 仅作为更大数据的载体；实现缩略图、短语音、图片分片、断点续传和失败回退。

**阶段 5：完善后台与隐私体验。** 分别适配 iOS 后台唤醒与 Android 前台服务/Companion 机制，加入权限解释、附近模式开关、隐私状态展示、紧急清除和本地数据备份/恢复说明。

**阶段 6：安全审查与公开测试。** 做协议 fuzz、密钥状态故障注入、重放测试、流量分析评估和第三方代码审查。完成后再决定是否扩大人数、媒体大小和后台承诺。

## 最应该立即修改的三件事

第一，把 README 从“功能愿望清单”升级为“产品边界 + 协议规范入口”，明确后台能力有系统限制，并写出第一版不支持什么。

第二，在没有写客户端之前，先建立共享核心和跨平台测试向量。不要让 Swift 和 Kotlin 各自解释同一个二进制协议。

第三，先做 BLE 单跳加密文字闭环，再做 Mesh 和媒体。只要单跳的身份、握手、重放防护、确认和队列没有稳定，多跳和大文件只会放大问题。
